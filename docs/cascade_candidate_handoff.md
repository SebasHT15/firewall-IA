# Delivering and measuring a V5 candidate

**Current candidate:** [Fast Path + V5.1](project_status.md), mode `FAST_PATH_V5`,
with `model2: null` in its [manifest](../reports/v5/fastv5-2026-11-11/manifest.EXPERIMENTAL.json).
Its six-app configuration is generated by `scripts/local_stack/challenges/challenge_stack.py`.
The Model 2-required delivery commands below describe the older `CASCADE_ACTIVE` experiments;
do not add Model 2 merely to follow that historical recipe. For the current lifecycle, read
[challenge apps](challenge_apps.md#current-candidate-2026-11-13).

What happens between new weights and a measured candidate. Nothing here approves a candidate, a
threshold or a deployment. 200 ms is an aspirational goal, and D36 is not rewritten.

## What the delivery must contain

| Part | Who | Notes |
|---|---|---|
| Adapter directory with `adapter_model.safetensors` | Model work | |
| Recipe | Model work | Its digest is the raw file's. The service reads it through `FIREWALL_V5_RECIPE` |
| Token measurement | Model work | JSON with a `measured` section: `max_length`, `margin`, `overhead`, `label_budget`, `B` |
| Model 2 artifact and policy | Model work | The policy must bind that artifact and feature view |
| Runtime decision | Model work | Native, or a profile written for **these** weights |
| Decoder verification | Model work | Only with a verified decoder: a JSON naming `profile_sha256` |

**The fast profile does not carry over.** A profile binds one adapter and one recipe. The current
`verified-suffix` profile binds the previous adapter, so `make_candidate_manifest.py` and the gateway
refuse it for new weights. Using that decoder needs a new profile and a new verification on the new
weights and vocabulary.

## Write the manifest

There is no default runtime. Choose one explicitly:

```bash
.venv-dataplane/bin/python scripts/gateway_ops/make_candidate_manifest.py --out <manifest.json> --manifest-id <id> --adapter-dir <dir> --recipe <recipe.json> --token-measurement <tokens.json> --model2-artifact <artifact.json> --model2-policy <policy.json> --native-runtime
```

With a profile, replace `--native-runtime` with `--runtime-profile <profile.json>`, and add
`--verification-evidence <evidence.json>` for a verified decoder.

`firewall-cascade-model-manifest/v2` adds to v1: `adapter_path`, `recipe_path`, `base_model`,
`base_revision`, `max_length`, `margin`, `overhead`, `label_budget`, `max_new_tokens` and `runtime`. v1
stays readable for the fixtures and runs that use it. A new candidate is v2.

| Refused | When | Reason |
|---|---|---|
| Profile of another adapter or recipe | Reading the manifest | The profile file says so |
| Profile bytes, status or schema | Reading the manifest | |
| Verified decoder without evidence, or evidence of another profile | Reading the manifest | |
| Vocabulary without ALLOW or BLOCK; `max_new_tokens` below `label_budget`; budget over `max_length` | Reading the manifest | |
| Adapter, recipe or decoder bytes | `launch.py --check`, `candidate_check.py` | Offline |
| Service with another adapter, recipe, template, vocabulary, base model, token contract or runtime | Readiness | Not ready, 503 to every request |
| Experimental manifest, policy or runtime in `production` | Enablement | |

## Check identity

No model, no GPU. Add `--v5-url` when a service is up. `--previous` compares with an earlier candidate:

```bash
.venv-dataplane/bin/python scripts/gateway_ops/candidate_check.py --manifest <manifest.json> --previous reports/v5/successor-2026-10-30/verified-suffix/service-final/cascade-manifest.EXPERIMENTAL.json --out <check.json>
```

`IDENTITY_CONSISTENT` says the files, the recipe and the service describe one candidate. It says nothing
about quality or latency.

The gateway configuration is `firewall-cascade-gateway-config/v2`. Point `manifest` at the candidate and
keep `canonical.max_received_body` at or below its `max_decoded_body`: a higher value refuses to start.

## Walk through the candidate

`GPU_STATUS.json` must show the hand-off: the script refuses without it. V4 takes no part.

```bash
.venv-dataplane/bin/python scripts/gateway_ops/candidate_walkthrough.py --manifest <manifest.json> --out <new directory> --work <private directory> --inputs /home/sebas/Documents/Codex/2026-10-26/ta/work/metrics-2026-10-30/inputs.private.jsonl
```

| Layer | What it establishes | What it does not |
|---|---|---|
| `mechanism` | Identity and readiness, each route, Model 2 failure → DEFER, each V5 failure → deny, independent reception, recovery | Anything about quality |
| `classification` | Decisions on the authored DEV cohort against authored references | Detection quality. References are expectations, and JWT/CSRF need state |
| `attack_effect` | Nothing. It is reported `NOT_MEASURED` | The sink proves delivery only |

Faults are injected by a forwarder between the gateway and V5, so a real service can fail in every way
without touching its weights. `--doubles` runs the mechanism layer with a V5 double, without GPU.

## Compare the modes, case by case

Sends every case of a delivered evaluation through the gateway, one at a time, and keeps classification,
action, HTTP status and independent reception apart:

```bash
.venv-dataplane/bin/python scripts/gateway_ops/candidate_compare.py --manifest <manifest.json> --mode V5_ONLY --cases <cases.private.jsonl> --wires <inputs.private.jsonl> --census <predictions.jsonl> --out <new directory> --work <private directory>
```

Repeat with `--mode CASCADE_ACTIVE`, into the same directory. Cases without a recorded wire get one built
from their canonical text. A forwarder hashes what V5 receives, so only `V5_ONLY` confirms the round trip
of every case: Model 2's early blocks never reach V5. `candidate_compare_report.py` joins the rows with the
censuses, the counterfactuals and the cases the delivery singled out.

## Traffic and operation trials

Phases, in order. Rates come from this candidate's own ladder:

```bash
EVIDENCE=<new dir> WORK=<private dir> MANIFEST=<manifest.json> scripts/gateway_ops/run_candidate_load.sh --phase ladder
```

```bash
.venv-dataplane/bin/python scripts/gateway_ops/load_analyze.py --run <new dir> --work <private dir> --out <new dir>/analysis-ladder.json
```

`soak_rates`, `soak_high_rate` and the first saturated rate are in that file. The recovery rate is 1.5 ×
the first saturated rate:

```bash
EVIDENCE=<new dir> WORK=<private dir> MANIFEST=<manifest.json> scripts/gateway_ops/run_candidate_load.sh --phase soak --soak-rates candidate=<R> --phase soakhigh --soak-high-rate <R> --phase recovery --recovery-rate <R> --phase failures --phase audit
```

```bash
.venv-dataplane/bin/python scripts/gateway_ops/load_analyze.py --run <new dir> --work <private dir> --out <new dir>/analysis.json --markdown <new dir>/TABLAS.md
```

| Asked for | Where |
|---|---|
| Offered load, complete responses, useful capacity | `client` of each step; `ladder` of the analysis |
| Rejections, errors, timeouts, cut bodies | `rejected_503`, `bad_gateway_502`, `connection_errors`, `client_timeouts`, `incomplete_body` |
| Time per stage and end to end, P50/P95/P99 | `soak_stages_pooled`, `soak_pooled` |
| Queues | `resources.queues` per step: admission, in flight, observation, V5 client, audit |
| Resources | `resources.roles`, `resources.gpu` |
| Recovery | `recovery`, `failures` |
| Audit: requested, completed, discarded, failed | `audit_accounting` per step, `/status`, `/metrics` |

Percentiles over repetitions come from the pooled rows, by nearest rank. They are never averaged. Rates
are given per repetition as mean and range. `candidate_load_summary.py` adds totals of every step, peaks,
pooled audit cells and the cases V5 could not answer.

Recovery ends at 10 consecutive clean probes. A case V5 cannot answer gives a 503 and restarts that count,
so read the probes before reading a long recovery as a slow drain.

Without an explicit `--soak-high-rate`, `soakhigh` is the same rate as `soak` when V4 takes no part. Use it
only with a higher rate, such as 0.7 x the lowest sustainable rate of `CASCADE_ACTIVE`.

`--with-v4` adds `V4_ONLY`, `CASCADE_OBSERVE` and the return to V4. It needs V4 loaded on the same GPU
and is left out by default.

## Dry run, without GPU

```bash
.venv-dataplane/bin/python scripts/gateway_ops/load_check.py --out <new dir> --work <private dir> --candidate-manifest <manifest.json> --inputs <private inputs.jsonl> --doubles --double-behavior serial --double-inference-ms 40 --quick --phase ladder --phase soak --soak-rates candidate=3 --phase soakhigh --soak-high-rate 4 --phase audit --phase recovery --phase failures
```

`serial` behaves like one GPU. Its times are the ones it was told to use, so a dry run proves the
harness, not a capacity.

## Restarting under traffic

mitmdump listens before its startup ends and exits on any error logged in that window. A denial while not
ready must therefore never log an error. `restart_under_traffic.py` checks it, with a V5 double.
