3a. THE ONE RECIPE-AFFECTING CHANGE:  fp16=True  ->  bf16=True
------------------------------------------------------------------------------
This was FORCED by the stack, not chosen. The first smoke attempt with the
recipe's original fp16=True crashed:

  File ".../accelerate/accelerator.py", line 2932, in unscale_gradients
    self.scaler.unscale_(opt)
  File ".../torch/amp/grad_scaler.py", line 279, in _unscale_grads_
    torch._amp_foreach_non_finite_check_and_unscale_(
  RuntimeError: "_amp_foreach_non_finite_check_and_unscale_cuda"
                not implemented for 'BFloat16'

  Crash occurred at step 0/12, in _clip_grad_norm during the first optimizer
  step. Model load, dataset tokenization, LoRA attachment and the forward pass
  all succeeded before it.

CAUSAL CHAIN (verified by reading the installed TRL source):
  1. trl/trainer/sft_trainer.py:1088-1092 — when the base model is 4-bit
     loaded, TRL casts EVERY trainable parameter to torch.bfloat16, following
     the QLoRA paper. There is no flag to disable this.
       "if getattr(model, 'is_loaded_in_4bit', False) ...:
            for param in model.parameters():
                if param.requires_grad:
                    param.data = param.data.to(torch.bfloat16)"
     Confirmed empirically — the run prints:
       dtype de parámetros entrenables: ['torch.bfloat16']
  2. fp16=True makes transformers/accelerate wrap the step in
     torch.amp.GradScaler.
  3. GradScaler.unscale_ dispatches to a CUDA kernel with no BFloat16
     implementation.

  => fp16 + 4-bit QLoRA cannot run on TRL 1.4.0 at all. This is structural.

RESOLUTION: bf16=True. bf16 requires no loss scaling, so the GradScaler path
  is not taken. The RTX 4090 Laptop (Ada, sm_89) supports bf16 natively
  (torch.cuda.is_bf16_supported() = True).

  `fp16` is not in the E1 protected-parameter list, so this did not trigger
  the STOP condition. It is nonetheless a numerics change and is recorded here
  rather than applied silently. It is reversible and reproducible:
      python3.12 finetune.py --smoke --force-fp16
  reproduces the crash above.

  bnb_4bit_compute_dtype was deliberately LEFT at torch.float16. It is
  quantization configuration (explicitly protected for E1) and changing it is
  not required to fix this. Aligning it to bfloat16 for consistency with the
  QLoRA reference configuration is a separate decision for the user.

7a. CORRECTION TO AUDIT FINDING F5
------------------------------------------------------------------------------
The audit stated that the ###END### embedding row is "randomly initialised",
"never saved", and "re-randomised on every load". On THIS stack that is
partly wrong, and the record is corrected here:

  WRONG  — "randomly initialised": transformers 5.8 mean-resizes new rows from
           a multivariate normal fitted to the existing embeddings' mean and
           covariance, not pure random init. (Log message confirms this.)
  WRONG  — "never saved" / "re-randomised on every load": PEFT force-saves both
           embedding matrices when a resize is detected, so the row IS
           persisted and IS deterministic across loads.
  CORRECT — the row receives NO gradient. modules_to_save=None and
           trainable_token_indices=None in the saved adapter_config.json
           confirm it. The token is saved at its initialisation value and
           never learns to be emitted.

  The conclusion (remove the token, per D5) is unchanged, but the mechanism is
  different from what the audit described, and the strongest argument for D5 is
  now the measured 12x adapter-size inflation rather than load non-determinism.

  TRL 1.4 does contain machinery that would fix this class of bug
  (trainable_token_indices={"embed_tokens": ...} plus an automatic
  modules_to_save=["lm_head"]), but sft_trainer.py:1037-1056 only fires it for
  tokens TRL itself adds via chat-template cloning — not for tokens added
  externally as finetune.py does.
