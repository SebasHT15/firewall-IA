2. NATIVE EOS — VERIFIED BEFORE ANY EDIT
==============================================================================
A stop condition for E4 was "native EOS behavior is ambiguous under the
installed stack". It is not. Measured on TinyLlama-1.1B-Chat-v1.0 with
transformers 5.8.0 / TRL 1.4.0:

  eos_token                        '</s>'
  eos_token_id                     2
  pad_token (pre-set)              '</s>'
  vocab_size / len(tokenizer)      32000 / 32000

  A literal "</s>" inside the formatted text tokenizes to the REAL eos id:
    text tail  "...no attack patterns detected.</s>"
    ids  tail  [694, 5337, 15038, 17809, 29889, 2]      last id == 2  -> True

  => format_example() has ALWAYS emitted a genuine native EOS. The custom token
     was never the actual termination mechanism.

  TRL 1.4 add_eos guard (trl/trainer/sft_trainer.py:1427):
    appends EOS only `if not example["text"].endswith(eos_token)`.
    The formatted text ends with "</s>", so TRL does NOT append a second EOS.

  CRITICAL SIDE-FINDING that shaped the edits:
    Without the tokenizer resize, `tokenizer.convert_tokens_to_ids("###END###")`
    returns 0 — the UNK token id. Any surviving `eos_token_id=end_token_id`
    override would therefore have silently set EOS to <unk>. Every such
    override was removed, not merely the token registration.
    (With the base tokenizer, "###END###" is 4 ordinary tokens:
     [835, 11794, 2277, 29937].)

9. ADAPTER / EMBEDDING PERSISTENCE
==============================================================================
Verified WITHOUT any training run: a PEFT model was constructed exactly as
finetune.py now does (4-bit NF4 base, no resize, same LoraConfig) and saved with
save_pretrained. The saved adapter was then inspected.

  adapter_config.json
    modules_to_save          = None
    trainable_token_indices  = None
  adapter_model.safetensors
    embed_tokens / lm_head tensors present : NONE
    total parameters                       : 12,615,680  (LoRA only)

  COMPARISON WITH E1 (which had the resize):
    E1  308 LoRA tensors  12,615,680 params
        + base_model.model.model.embed_tokens.weight  [32001, 2048]
        + base_model.model.lm_head.weight             [32001, 2048]
        = 131,076,096 extra params, ~250 MiB, adapter total ~298 MB
    E4  308 LoRA tensors  12,615,680 params, and nothing else.

  CONCLUSION, stated exactly as the evidence supports:
    "The structural cause of the E1 embedding/head inflation has been removed."

  NO production adapter size is claimed. The probe file measured 48.2 MiB
  because a bare get_peft_model keeps LoRA params in fp32 (12,615,680 x 4 B);
  under the real training path TRL casts trainable params to bf16 for 4-bit
  models (D11), which is why E1 measured ~24 MiB of LoRA tensors. The dtype,
  not the token, explains that difference. An exact production figure requires
  an actual training run and is deliberately not asserted here.

  NO LATENCY IMPROVEMENT IS CLAIMED. Under the old configuration
  eos_token_id pointed at a token the model could not emit, so generation
  plausibly always ran to max_new_tokens=40; native EOS may terminate earlier.
  That remains a HYPOTHESIS until measured with a trained model (D5).
