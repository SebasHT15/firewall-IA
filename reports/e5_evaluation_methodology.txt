3. LEVEL 1 — BINARY SECURITY DECISION
==============================================================================
POSITIVE CLASS: BLOCK. The security question is "did we catch the attack?", so
the attack class is positive. This convention is fixed in code as
POSITIVE_CLASS and must never be switched silently.

CONFUSION MATRIX (rows = expected, cols = predicted)

                    pred BLOCK        pred ALLOW
    exp BLOCK       TP                FN
    exp ALLOW       FP                TN

DEFINITIONS — stated explicitly so they cannot drift:

  TP   expected BLOCK, predicted BLOCK    attack correctly blocked
  FN   expected BLOCK, predicted ALLOW    ATTACK MISSED — most serious error
  FP   expected ALLOW, predicted BLOCK    benign traffic wrongly blocked
  TN   expected ALLOW, predicted ALLOW    benign traffic correctly allowed

  support                 TP + FP + FN + TN
  correct decisions       TP + TN
  accuracy                (TP + TN) / support
  precision (BLOCK)       TP / (TP + FP)
  recall (BLOCK)          TP / (TP + FN)
  F1 (BLOCK)              2PR / (P + R)
  attack detection rate   TP / (TP + FN)   — identical to recall by definition;
                          reported under both names because the security
                          literature uses "detection rate"
  false positive count    FP
  false positive RATE     FP / (FP + TN)   — denominator is the BENIGN
                          population, not all traffic
  false negative count    FN
  false negative RATE     FN / (TP + FN)   — denominator is the ATTACK
                          population, not all traffic

  FPR and FNR are deliberately normalised over their own class populations.
  Dividing either by total traffic would understate both.

FALSE POSITIVE RATE IS REPORTED SEPARATELY AND PROMINENTLY. For an inline
gateway it is the operational cost metric, and it must never be buried inside
overall accuracy. The v4 eval split provides 3,103 benign examples, versus 26
in the legacy suite — the first population large enough to support an FPR
statement at all.

4. LEVEL 2 — ATTACK CATEGORY / REASON
==============================================================================
THE CRITICAL SEPARATION. Given:

    expected   BLOCK | SQL injection payload detected.
    predicted  BLOCK | Cross-site scripting payload detected.

  binary security decision  = CORRECT   (the attack WAS blocked)
  category / reason         = INCORRECT

  A category mismatch is NOT a security failure and NEVER reduces binary
  recall. This is enforced structurally: reason accuracy is computed only over
  examples that were already counted as correctly blocked, so the two
  dimensions cannot contaminate each other. Verified by fixture
  ("binary recall 2/3 (mismatch still blocked)" / "reason accuracy 1/2").

REASON MATCHING POLICY — objective, no subjective mapping:
  normalize_reason() applies casefold, whitespace collapse, and removal of a
  single trailing period. A predicted reason either equals a canonical dataset
  reason under that normalisation, or it does not. There is NO synonym table,
  NO keyword heuristic, NO partial-credit scoring.

  This is defensible because the model is trained on exactly 19 fixed reason
  strings, so exact match is the intended behaviour rather than an arbitrary
  bar. Verified unambiguous: all 6,206 eval labels conform to
  "DECISION | reason", 19 distinct strings, 0 non-conforming, 0 multi-pipe.

PER-CATEGORY REPORTING — every percentage carries its sample count:

  category
  support                        expected-BLOCK examples in this category
  binary recall  num/den         blocked correctly / support
  reason accuracy num/den        reason matched / blocked correctly
  invalid outputs
  evidence status                OK | INSUFFICIENT DATA | NOT EVALUABLE

  A percentage is NEVER printed without its numerator and denominator.

5. INSUFFICIENT-DATA POLICY (D18)
==============================================================================
NOT EVALUABLE — zero held-out support. No accuracy, recall, or any other
category-level claim may be made.

    HTTP Request Smuggling     7 train rows, 0 eval rows

  Confirmed present in the manifest as not_evaluable_categories and verified by
  fixture. Per D18 no samples were generated or moved to make it evaluable, and
  the grouped split was not weakened.

INSUFFICIENT DATA — flagged from two independent sources, whichever fires:
  (a) the category appears in the manifest's insufficient_data_categories
      (fewer than 100 unique LOGICAL GROUPS), mapped to its reason string
      through the generator's own CATEGORY_SHAPES/HARDCODED_SHAPES tables so
      the two can never drift apart; or
  (b) held-out support < MIN_EVAL_SUPPORT (30).

  Ten categories are currently flagged, with their eval support:
      CRLF injection                112
      XML external entity            27
      GraphQL injection              22
      LDAP injection                 21
      NoSQL injection                17
      JWT token manipulation         16
      XPath injection                11
      CSRF                            8
      Insecure deserialization        5
      HTTP parameter pollution        3

  Note CRLF has 112 eval rows but only 21 unique logical groups — rule (a)
  catches it where a support-only rule would not. Group scarcity and row
  scarcity are different failure modes and both are checked.

  Results for these categories are EXPLORATORY. They are printed with raw
  numerator/denominator and an explicit status column, and must not be
  presented as robust category-level conclusions.

  Well-supported categories (status OK): SQL injection (817), XSS (708),
  Path traversal (506), File inclusion (494), Command injection (134),
  SSTI (88), SSRF (63), Open redirect (51).

6. INVALID-OUTPUT POLICY
==============================================================================
Parsing uses the E4 contract regex, byte-identical to classifier_api.py:

    \b(ALLOW|BLOCK)\b\s*\|\s*(.+?)\s*(?:\.|\n|$)

  The FIRST valid decision is extracted. Defensive against leading/trailing
  whitespace, a missing trailing period, a missing space before the pipe, and
  any continuation text after the reason.

  If no decision can be extracted the result is INVALID. It is NOT coerced.
  (The pre-E5 code silently fell back to "BLOCK if 'BLOCK' appears in the text
  else ALLOW", which manufactured a decision from garbage. That fallback is
  removed from the evaluation path.)

  FROZEN TREATMENT: an invalid output is counted as an incorrect security
  decision and mapped to the OPPOSITE of the expected decision, so it can never
  earn credit:
      expected BLOCK + invalid -> FN
      expected ALLOW + invalid -> FP

  Additionally reported:
      invalid_outputs, invalid_output_rate
      a PARSEABLE-ONLY confusion matrix and metric set, so the effect of the
      mapping is always visible and never hidden.

  RELATIONSHIP TO D4: D4 specifies FAIL-CLOSED runtime behaviour — an unusable
  classifier response blocks traffic. That is an operational control, NOT
  evaluation credit. A model emitting garbage is not detecting anything. The
  two concerns are deliberately kept separate.

7. LEVEL 3 — LATENCY
==============================================================================
NOT MEASURED IN E5. V4 is untrained, so no latency benchmark was run. The code
records per-example latency and computes the full distribution, ready for the
first real run.

  Reported: count, mean, P50, P95, P99, min, max, stdev.
  Percentiles use nearest-rank. Verified on 1..100 -> p50=50, p95=95, p99=99.

  Average alone is never reported.

  SCOPE DISCIPLINE: test_model.py measures MODEL-SIDE INFERENCE ONLY — the
  generate() call. It excludes proxy overhead, API overhead and network time,
  and every emitted record is stamped with that scope string.

  D3's target of end-to-end added latency P95 <= 200 ms is an END-TO-END budget
  covering proxy + API + model. A model-only number is NOT comparable to it and
  must not be presented as satisfying or failing it. Decomposed measurement
  (model-only / model+API / proxy / end-to-end) belongs to a later phase.

==============================================================================
8. LEGACY MANUAL SUITE
==============================================================================
ROLE: MANUAL DIAGNOSTIC / REGRESSION SUITE. Preserved in full, unchanged —
135 cases (95 systematic + 20 adversarial + 20 false-positive).

  Legitimate uses: known edge cases, qualitative inspection, regression checks
  between model versions.

  NOT legitimate: the headline V4 metric. Reasons, printed as a banner whenever
  the mode runs:
    * composition is 109 BLOCK / 26 ALLOW — an always-BLOCK classifier scores
      80.7%, so accuracy on it is only ~10 points above a degenerate baseline;
    * 26 ALLOW cases cannot support an FPR claim (0/26 has a 95% upper bound
      near 11% by the rule of three);
    * 5 cases per category gives 20-percentage-point resolution;
    * its adversarial cases reuse transform families that also appear in
      training augmentation.

  Access: --mode manual. It is never mixed into --mode dataset output.

==============================================================================
9. ADVERSARIAL EVALUATION — DEFERRED
==============================================================================
NOT IMPLEMENTED, deliberately.

  The current adversarial cases are NOT sufficient evidence of evasion
  resistance, because their transform families overlap the training-pool
  transforms used for augmentation in E2/E3 (url_encode, case_variation,
  sql_comment_inject, whitespace_tab). Measuring them therefore measures
  learned transforms, not evasion resistance.

  A future adversarial evaluation must distinguish:
    * SEEN transform families (training pool)
    * HELD-OUT transform families — reserved and unused per D15:
      double_url_encode, unicode_escape, html_entity, bash_ifs,
      mixed_case_percent, param_fragmentation
    * HELD-OUT base payload identities

  This is future work AFTER the clean baseline exists.

12. KNOWN LIMITATIONS
==============================================================================
  1. NO MODEL RESULTS EXIST. Every number in this document is a definition or a
     fixture, never a measurement of model behaviour.
  2. Reason matching is exact-after-normalisation. A semantically reasonable
     but differently-worded reason scores as incorrect. This is intentional
     (the model is trained on 19 fixed strings) but it makes reason accuracy a
     STRICT metric that should not be compared against loosely-scored figures
     from other work.
  3. Eleven categories cannot support robust per-category conclusions; one is
     unevaluable entirely. This is a dataset-scarcity limit, not a metric one.
  4. Evasion resistance is unmeasured by design (section 9).
  5. Latency is model-only and not comparable to the D3 end-to-end budget.
  6. The eval split's benign population is synthetic + CSIC 2010. A low FPR on
     it does not establish a low FPR on live production traffic.
  7. CSIC BLOCK labels come from an 11-rule keyword heuristic (audit F6), so
     the CSIC portion of any per-category result inherits that circularity.
  8. No statistical confidence intervals are computed. For small-support
     categories the point estimates are wide; the raw num/den is printed so a
     reader can compute an interval, but the tool does not.
