1. METHOD — SOURCE-STRATIFIED, GROUP-PRESERVING ROUND ROBIN
==============================================================================
The rendered-row cap is applied to malicious (BLOCK) categories only, AFTER
valid rendering and deduplication and BEFORE final method-stratified balancing.
Benign traffic is never row-capped.

Exact selection method, per capped category:

  1. SPLIT QUOTA. The category's row budget is divided between train and eval
     in proportion to their current row counts, so the grouped split's
     train/eval ratio is preserved and no group is moved between splits.

  2. SOURCE QUOTA. Within a split, the budget is divided between the two
     sources — PayloadsAllTheThings/hardcoded and CSIC — in proportion to
     their current row counts, by largest remainder. This is what prevents
     "trivially deleting one entire source first": at every cap tested, both
     sources survive in proportion to their natural presence.

  3. GROUP ROUND ROBIN. Within a source stratum, rows are taken one per
     logical group across all groups, then a second per group, and so on until
     the quota is met. This deliberately spends the budget on BREADTH before
     DEPTH, so a row cap removes row REDUNDANCY before it removes logical
     DIVERSITY.

  4. DETERMINISM. Groups are ordered by group id; rows within a group are
     ordered by sha256 of their content. Selection is therefore deterministic
     and independent of iteration order.

VERIFIED BEHAVIOUR-PRESERVING: after adding the row cap, re-running the default
configuration reproduced datasets/v4_clean/{train,eval}.jsonl BIT-IDENTICALLY.

  FINDING — the threshold is arithmetic, not empirical.
    A category cannot represent G logical groups in fewer than G rows. When
    row_cap < group_cap the round robin runs out of budget on its FIRST pass,
    so group retention is pinned at exactly row_cap / group_cap. At row2000
    that is 2000/2500 = 80.0%, observed exactly, in all four capped categories.

    => The safe floor is row_cap >= group_cap. Below it, the row cap destroys
       logical diversity by construction, which is the failure mode the task
       asked to be flagged.

  ABOVE the floor the behaviour is exactly the desirable case named in the
  task: SQL Injection falls 5,545 -> 3,000 rows (-45.9%) while retaining
  2,425 of 2,500 logical groups (97.0%), and at 3,500+ it retains 100%.
  Row capping is removing REDUNDANT RENDERINGS of already-represented payloads,
  not distinct attack material.

  ROWS PER REPRESENTED GROUP, before and after (g2500B_row3000):
    CRLF Injection      24.33 -> 1.62      SQL Injection   6.35 -> 1.24
    XSS Injection        2.08 -> 1.20      Path Traversal  1.00 -> 1.00
  After row capping no category exceeds 1.67 rows per represented logical
  group. The redundancy that made row counts a misleading proxy for diversity
  is gone.

  NOTE ON DENOMINATORS: the previous report's "24.33 rows/group" for CRLF used
  ATTACK logical groups only (21). The 1.62 figure here uses REPRESENTED groups
  (315 = 21 PayloadsAllTheThings + 294 CSIC). Both are correct measures of
  different quantities; CRLF itself was never row-capped (511 rows < any cap
  tested). This is a denominator change, not an effect of the row cap.

  vs cap2000_B — g2500B_row3000 DOMINATES ON BALANCE AT EQUAL SIZE
    3% smaller (28,084 vs 28,978), but largest share 21.4% vs 31.4% — TEN
    points better — top-3 61.2% vs 65.9%, eff.cat 7.89 vs 7.45. It gives up
    1,068 CSIC BLOCK rows (3,128 vs 4,196). For a 3% size reduction it buys a
    32% relative reduction in single-category dominance.

  vs cap2500_B — g2500B_row4000 IS THE BETTER-BALANCED, SMALLER OPTION
    9% smaller (31,340 vs 34,430) with largest share 25.5% vs 32.2% and
    eff.cat 7.42 vs 6.93, retaining 3,906 of 4,937 CSIC BLOCK rows (79%).

  WHY THE HYBRID BEATS GROUP-CAP-ONLY
    A group cap cannot reach the redundancy that CSIC groups emit — capping
    groups at 2,500 still left SQL Injection at 5,545 rows because its CSIC
    groups render many records each. The row cap acts directly on the quantity
    that determines training contribution, and because it spends its budget
    breadth-first it does so at almost no cost in logical diversity above the
    row_cap >= group_cap floor.

9. LIMITATIONS
==============================================================================
  1. No model was trained. Every figure is a DATASET property. Whether lower
     dominance improves per-category recall is untested.
  2. The group cap was held at 2,500 throughout, as instructed. Joint
     (group, row) optimisation was not explored; a lower group cap with a
     similar row cap might retain more CSIC traffic at equal balance.
  3. Only uniform per-category row caps were tested — no per-category budgets.
  4. The row cap operates on whole rendered rows. Sub-sampling records WITHIN a
     CSIC group before rendering was not tested and would be a different
     tradeoff between CSIC row count and CSIC shape diversity.
  5. Content-Type drifts upward as the cap tightens (§5). Small, but it is a
     mechanism that would matter if far tighter caps were ever considered.
  6. Scarcity and the Request Smuggling zero-eval problem are untouched.
