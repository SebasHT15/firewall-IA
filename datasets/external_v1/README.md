## Why `spec_preview.jsonl` has `request_text: null`

Ground truth and provenance intent are authored **before** capture. But a candidate's frozen
`request_text` is **the bytes a real client actually put on the wire, as the capture proxy
renders them** — never a hand-written string (protocol §4.2). So `preview_text` in
`spec_preview.jsonl` is the authoring *intent* (target + the headers we set); the real
`request_text` (with the client's own `User-Agent`, `Accept`, framing) is attached by
`label_candidates.py` from the capture and is **copied verbatim, never edited**.

The two **browser** slices are not previewable at all: Chromium emits its own sub-resource
requests, so those slices are captured whole and labelled entirely from the capture.

## Architecture (Phase C)

```
real client  ──►  capture-proxy (CAPTURE-ONLY)  ──►  lab-app
  curl/httpx        data-plane image running            inert, deterministic,
  Playwright        capture_addon.py; imports            append-only receipts
                    data_plane.render_request;
                    classifies nothing, blocks
                    nothing, no control plane
```

No firewall data plane, no control plane, no model in the path (D37). Flows are separated by
**capture-file offset windows** (`boundaries.json`), so no marker, correlation id or test
header is ever added to a request under test (protocol §11).

## How to build the DRAFT candidates (Docker handoff)

Your terminal has Docker; this session may not. Run these, and paste the output — nothing
below is assumed to have succeeded until you do.

**0. Build the images** (data-plane image is reused by capture-proxy):
```bash
docker compose build data-plane lab-app generator
```
Expected: three images build; `firewall-ia/data-plane:lab`, `firewall-ia/lab-app:lab`,
`firewall-ia/generator:lab`. Control-plane is NOT built (it loads the model — keep it down).

**1. Bring up only lab-app + the capture proxy** (a fresh capture file, separate from the
Phase B `capture.jsonl`):
```bash
CAPTURE_FILE=extv1-draft.jsonl docker compose --profile extv1 up -d lab-app capture-proxy
```
Expected: `lab-app` becomes healthy, then `capture-proxy` starts and prints
`capture proxy ready: ... policy=CAPTURE-ONLY`. Control-plane and data-plane stay stopped.

**2. Run the whole DRAFT capture in one command:**
```bash
docker compose --profile extv1 run --rm generator \
  python3 run_capture.py \
    --proxy http://capture-proxy:8081 \
    --shop http://shop.fwlab.test:9100 \
    --capture-file /logs/capture/extv1-draft.jsonl \
    --boundaries /logs/capture/boundaries.json
```
Expected: a per-flow summary. The eight enumerable flows must print `captured N (expected N)`
with **no `<-- MISMATCH`** (each spec = exactly one request). The two browser flows print
their captured counts (variable, should be ≥ 40 each). Writes
`docker/.lab-logs/capture/extv1-draft.jsonl` and `.../boundaries.json`.

**3. Assemble the labelled candidates (host-side, no Docker):**
```bash
.venv-dataplane/bin/python scripts/external/label_candidates.py \
  --capture docker/.lab-logs/capture/extv1-draft.jsonl \
  --boundaries docker/.lab-logs/capture/boundaries.json
```
Expected: `candidates assembled: ~480` (BLOCK 254 enumerable; ALLOW = 140 enumerable +
whatever the two browser slices captured, ~40–50 each), a per-cell count table,
`review status`, and `PROBLEMS (0)`. Writes `candidates/<cell>.jsonl`,
`candidates/cases_draft.jsonl`, `candidates/realized_counts.json`. Status stays **DRAFT**.

**4. Tear down:**
```bash
docker compose --profile extv1 down
```

*Optional — re-verify capture fidelity on this DRAFT:* Phase B already proved this exact
